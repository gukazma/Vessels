# 三国小队战术游戏：从 0 到 1 开发方案

本文是可随试玩反馈调整的开发路线。当前 **M0 控制与移动原型已经实现，等待用户试玩验收**；后续任务均未开始。任务通过代码检查不等于玩法通过验收，阶段结束必须实际试玩。

## 1. 游戏定位与核心体验

方向是 **《英雄连》式小队即时战术 + 三国武将与领土经营**。玩家选择武将率领的小队，下达移动、占位、攻击、撤退和技能命令；士兵自主执行。它不是自走棋，也不采用《英雄无敌》的英雄带兵回合战斗。旧丧尸项目的题材、美术和战斗规则不作为新游戏设计约束。

最希望玩家说出的一句话：**“我兵比对面少，但看准了地形和侧翼，拿下了这座城，还收服了对方的将领。”**

玩法围绕三个支点展开：

- **少而清楚的战场决策**：每支队伍有明确职责，绕路、掩护、侧击和撤退都能改变战果。
- **能解释的以弱胜强**：胜负来自地形、朝向、士气与补给；战后能看懂哪一步起了作用。
- **有后果的扩张**：士兵伤亡需要补充，武将需要招募；占领城市决定下一场仗的选择。

武将采用克制的历史演义表达：有个人特长和主动号令，但不能独自砍翻整支军队。兵种不会靠固定标签瞬间相克；例如枪兵迎面结阵能挡骑兵，而从背后受冲锋仍然危险。不设法术兵种。阵地压制体现为箭矢威胁、人员受伤与士气变化，不照搬机枪规则。

**单次循环**：观察地形与敌情 → 编组选将 → 下令与调整队形 → 争夺据点或击溃敌军 → 收拾伤兵和俘虏 → 招募或补充 → 决定下一处进攻目标。

## 2. 第一版做到什么程度

先做一段能够从新游戏玩到结局的单机垂直切片，验证上面的循环；它不是包含整个三国时代的商业完整版本。

| 范围 | 第一版边界 |
| --- | --- |
| 运行平台 | Windows 桌面端，Godot 4.6.1，鼠标与键盘 |
| 画面 | 俯视 2D 灰盒先行；战术可读性通过后再确认正式美术 |
| 战场 | 1 张野战地图、1 张攻城地图；交战初期敌情可见，后续加入视野与简单侦察 |
| 部队规模 | M0 为玩家 3 支小队，每队 1 名领队 + 6 名士兵；完整切片上限双方各 6 队，共 84 个角色 |
| 兵种 | 盾步兵、枪兵、弓兵、轻骑兵 4 类；兵种逐步加入，不要求 M0 实现 |
| 武将 | 6 名具有不同特长的候选武将；具名武将带队，空缺可由普通领队代替 |
| 战略层 | 3 座相连城市、玩家与 1 个敌对势力；1 回合为 1 天 |
| 战役 | 玩家从 1 城出发，在限定局势下夺取其余 2 城；有胜利和失败结局 |
| 经营 | 金钱、粮草两类资源；补兵、募将、出征三个主要支出 |
| 招募 | 在野武将事件和俘虏劝降两条路径；条件透明，第一版不设隐藏随机失败率 |
| 保存 | 本地单存档槽、战略阶段手动保存与回合结束自动保存；不支持战斗中途保存 |

实时战斗允许暂停下令，恢复后按命令执行，降低多队操作门槛。战略层用一天一回合，让行军与短期补给的代价容易理解；不模拟实时赶路，也不让同一支队伍一天内连续攻下多城。地图规模扩大后再考虑旬制，不在第一版同时实现两种时间尺度。

首版不做多人联网、开放世界、完整中国地图、全历史武将、复杂外交、婚姻家族、装备刷宝、科技树、可破坏的全部建筑、攀墙与多层城内巷战。这些内容只有在核心战术和扩张循环成立后再排序。

## 3. 核心规则：先有取舍，再加数量

### 指挥与战斗

- 小队是选择和命令单位，士兵是阵型与战斗表现单位。领队倒下不会立即删除全队，而会造成士气冲击；最终伤亡结算在战斗结束统一完成。
- 一次右键命令有明确含义：空地移动、敌军攻击、可交互目标占领。第一版不加入大量隐式快捷组合。
- 停止命令取消当前路线和待执行命令；撤退命令则主动朝安全点离场，两者必须区分。
- 阵型分配和小队路径分别处理；绕过障碍时允许暂时收缩，抵达开阔地后恢复，不能为了保持整齐穿墙。
- 每个兵种先做一个核心职责和一个限制，再添加武将技能。例如盾兵能稳住正面但追击慢，弓兵能施压但被贴近后脆弱。

### 弱胜强的规则链

| 决策 | 初始规则 | 玩家如何读懂 |
| --- | --- | --- |
| 利用掩体 | 矮墙、土垒为受保护方向提供远程伤害减免；近战不享受相同减免 | 显示掩体图标、保护方向与受击反馈 |
| 正面牵制 | 盾兵正面防护较强；转身有时间成本 | 面向标记清晰，不能瞬间全方向防御 |
| 侧翼进攻 | 侧后受击降低正面防护收益，并额外损失士气 | 明确的“侧击”提示，战报记录来源 |
| 击溃敌军 | 士气受伤亡、侧击、孤立和领队倒下影响；溃败者撤退而非战至最后一人 | 士气条、动摇/溃败状态可见 |
| 切断补给 | 战场补给点为附近非交战小队补给；被占后不能继续恢复 | 地图标出补给范围和剩余供给 |
| 保存兵力 | 撤退成功保留幸存者，重新整编有时间或资源成本 | 撤退路线与结算伤亡一致 |

数值先作为可调假设：士气范围 0–100，低于 20 进入溃败，脱战恢复到 45 才能重新接受战斗命令；两个阈值避免反复切换状态。掩体和侧击倍率经试玩确定，不在策划中写死一套“平衡答案”。

第一个战术验证关：玩家 3 队面对敌军 5 队。正面持续硬攻应明显不利；玩家可以用盾兵守住窄口、弓兵保护侧路、轻骑兵绕后夺取补给，再攻击动摇的敌队。关卡必须允许至少两种可复现的获胜思路，不能仅靠踩中预设触发点让敌人自动死亡。

### 武将与招募

每名武将只保留姓名、统率特长、一个被动、一个主动号令及招募条件。例如擅守者提高附近友军的士气恢复，擅袭者缩短脱战后再次突袭的准备时间。技能应强化战术选择，不覆盖兵种弱点。

在野招募用“满足声望/支付费用/完成一个事件”表达需求；俘虏招募用“释放、留押、满足条件劝降”产生选择。同一具名武将只能存在一份实例，转投后从原势力移除。第一版不做日常忠诚度衰减与随机叛变，以免战术之外增加难解释的惩罚。

### 战略与攻城

城市通过邻接路线连接。每支军队每天只能行军或发动一次进攻；先显示预计消耗，再确认出征。粮草不足限制持续作战和补兵，不直接在玩家不知情时抹除军队。

攻城地图先采用“城外接近 → 冲车破门 → 争夺城内据点”三段目标。攻方需要掩护一台冲车，守方能出城袭击冲车或侧击攻方；破门后仍需占住据点才能获胜。城墙作为通行与射界障碍，不做可攀爬的独立楼层。多入口、云梯、水攻等在这个版本通过后再决定。

## 4. 分阶段开发清单

共 29 个小任务。每次只推进一个可独立验收的任务或紧密相关的小组，完成后提供可运行版本、实际操作方式和已知限制。下面的顺序可因反馈调整，依赖不能跳过。

### M0：先把“指挥一支队伍”做顺手（当前计划待验收）

| ID | 小任务 | 依赖 | 实际验收 |
| --- | --- | --- | --- |
| M0-01 | 独立 Godot 工程与灰盒训练场 | 无 | 新工程能单独启动，场景中有地面、静态障碍及 3 支可辨识队伍 |
| M0-02 | 镜头移动、缩放与聚焦 | M0-01 | WASD、中键拖动、滚轮正常；F 聚焦选中队伍；缩放不能丢失整个场地 |
| M0-03 | 单选、框选与取消选择 | M0-01 | 点击任一队员选中整队；框选选中涉及的小队；Esc 清空；选中反馈清晰 |
| M0-04 | 多队移动、绕障碍、停止与基本队形 | M0-03 | 右键下令后各队有不同落点；反复穿过通道不穿墙、不永久卡住；停止立即取消路线 |

本阶段不包含攻击、敌人、经济和招募。需要用户试玩反馈：**镜头是否舒服、能否看清选中的是哪队、右键移动是否符合预期、队伍聚散是否自然。** 优先修这些问题，再做战斗。

### M1：让第一场小规模战斗成立

| ID | 小任务 | 依赖 | 实际验收 |
| --- | --- | --- | --- |
| M1-01 | 小队/兵种数据与生命、阵营 | M0-04 | 两个阵营正确识别，伤害与死亡可复现，阵亡者退出占位及目标列表 |
| M1-02 | 近战、远程、射程和基本目标选择 | M1-01 | 盾兵能接敌，弓兵在射程内攻击；墙挡住箭矢；不会隔墙近战 |
| M1-03 | 攻击命令与有限状态敌军 AI | M1-02 | 敌人能警戒、接敌、追击并停止无效追击；玩家可切换目标，无锁死状态 |
| M1-04 | 战术暂停与战斗命令队列 | M1-03 | 暂停时战斗不推进但能下令；恢复后有序执行；停止命令清掉旧命令 |
| M1-05 | 小遭遇战目标、胜负与重开 | M1-04 | 2 对 2 战斗可以获胜、失败、重开；战报伤亡与实际单位一致 |

需要用户反馈：**交战速度是否合适、是否看得懂谁在攻击谁、暂停有没有帮助、失败原因能否说清。** 如果基础交战只是站桩换血，不增加兵种数量来掩盖问题。

### M2：验证以弱胜强，而非堆数值

| ID | 小任务 | 依赖 | 实际验收 |
| --- | --- | --- | --- |
| M2-01 | 有方向的掩体与面向 | M1-05 | 同一弓兵攻击掩体正面和背面产生不同结果；界面能预判保护方向 |
| M2-02 | 士气、侧击与撤退 | M2-01 | 包抄能让敌队动摇/溃败；撤退可保住幸存者；恢复阈值不造成状态抖动 |
| M2-03 | 补给据点与简化视野侦察 | M2-02 | 占点能切断敌军恢复；未看见的敌人不能被直接点选攻击；最近目击信息区别于实时信息 |
| M2-04 | 枪兵、轻骑兵与 3 对 5 野战关 | M2-03 | 枪阵正面能阻骑兵，绕后有效；至少两种战术能赢，纯正面打法明显吃亏 |

需要用户反馈：**哪一次操作让你觉得自己扭转了战局；掩体、侧击、补给中哪些有趣，哪些只是额外负担。** 这是项目最重要的继续投入门槛；战术没有成立，战略地图后延。

### M3：让武将值得招、值得保护

| ID | 小任务 | 依赖 | 实际验收 |
| --- | --- | --- | --- |
| M3-01 | 稳定武将 ID、名册与编队 | M2-04 | 同一武将不能进入两队；调换领队后能力与界面一致 |
| M3-02 | 6 名候选武将与少量号令 | M3-01 | 每个技能有清楚范围、冷却和效果；至少两种不同编队能改变野战打法 |
| M3-03 | 在野招募事件 | M3-01 | 需求、费用、获得武将都可见；取消不扣款；重复点击不重复招募 |
| M3-04 | 俘虏、劝降与战后伤亡结算 | M3-02、M3-03 | 胜负均正确保留幸存者；俘虏招募成功后只属于一个势力，不生成复制武将 |

需要用户反馈：**是否因为某名武将的能力想要招募他；是否愿意为保住部队而撤退；选择是否只是“数值最大的一位”。** 此时再确认正式武将名单与历史人物表现，不先录入几百个人物。

### M4：把战斗放进三城战略循环

| ID | 小任务 | 依赖 | 实际验收 |
| --- | --- | --- | --- |
| M4-01 | 三城地图、归属与日回合 | M3-04 | 玩家和敌方轮流推进；城市收益每天只结算一次；不能跳过敌方行动重复领钱 |
| M4-02 | 金钱、粮草、补兵与募将 | M4-01 | 费用预览与实际扣除一致；资源不足不可执行；不会产生负数或重复收费 |
| M4-03 | 相邻行军、出征与战后返回 | M4-02 | 地图选择的军队准确进入野战，结算回写兵力和领队；同一军队当天不能反复行动 |
| M4-04 | 敌方一次合理战略行动与失城 | M4-03 | 敌方能补兵或攻打相邻城市；玩家可能失城；无资源时不会凭空生成满编军队 |

需要用户反馈：**打下一座城是否改变下一步选择；粮草是否带来有意义的取舍；补兵与招募是否拖慢节奏。** 第一版每座城一个主要特色，避免同时堆建设树和政令。

### M5：做出一场完整攻城战

| ID | 小任务 | 依赖 | 实际验收 |
| --- | --- | --- | --- |
| M5-01 | 城墙、城门、内城据点与通行 | M2-04 | 关门时不可通行或隔墙攻击；开门/破门后路线可靠更新 |
| M5-02 | 冲车与掩护、破门规则 | M5-01 | 冲车能被保护、受损、破坏；敌军可出击；没有冲车时仍有明确重试或撤退路径 |
| M5-03 | 攻守 AI 与连续阶段目标 | M5-02 | 守军会守门或出击；破门不直接宣告胜利，争夺内城据点才完成目标 |
| M5-04 | 攻城接入战略归属与俘虏结算 | M5-03、M4-04 | 战斗胜利后城池只转移一次；失败正确退回并结算损失；战略状态与战报一致 |

需要用户反馈：**攻城是否有不同于野战的决策；破门过程是否无聊；守军出击是否提供反制机会。** 不通过就调整关卡与目标，不立刻增加云梯和城内楼层。

| ID | 小任务 | 依赖 | 实际验收 |
| --- | --- | --- | --- |
| M6-01 | 战略存档、版本号与恢复 | M5-04 | 保存退出再进入，城市、资源、军队、俘虏与日期完全一致；坏档有明确提示且不覆盖有效备份 |
| M6-02 | 新游戏、引导、战役结局与重开 | M6-01 | 不用开发控制台能完成野战、招募、攻城、统一三城；失败后能重新开始 |
| M6-03 | 战术可读性与正式美术小样 | M6-02 | 敌我、兵种、朝向、掩体和士气在正常缩放下可辨；先比较一张场景小样再扩大美术制作 |
| M6-04 | 回归、性能、导出与完整试玩 | M6-03 | 在目标电脑连续完成一局，最大规模战斗无持续卡顿；Windows 导出包能独立启动和存取档 |

需要用户反馈：**是否愿意马上再玩一局；最值得保留和最想删除的机制各是什么。** 通过后再决定继续做内容量、历史剧本或多人模式，而不是预先承诺全部实现。

## 5. 工程组织与数据职责

新项目放在 `games/three_kingdoms/`，使用独立 `project.godot`。仓库现有项目继续保留，新项目不直接引用它的战斗脚本或旧题材素材。以下是逐步形成的职责分工，目录在实际需要时创建，不先生成大量空模块。

```text
games/three_kingdoms/
  project.godot
  scenes/                 # 入口、训练场、野战、攻城与战略地图的场景组合
  scripts/
    camera/               # 镜头输入、边界与缩放
    command/              # 选择、命令与队列，负责玩家意图
    units/                # 小队、士兵、阵型与局部移动
    combat/               # 伤害、目标、士气、掩体与视野规则
    campaign/             # 城市、每日结算、行军与战后回写
    recruitment/          # 武将名册、招募条件与所有权
    persistence/          # 存档结构、校验与版本迁移
    ui/                   # 面板和反馈，读取状态、发出命令
  data/                   # 兵种、武将、技能、地图与初始战役定义
  assets/                 # 实际运行需要的贴图、字体、声音
  tests/                  # 规则测试、场景烟测与必要的存档样例
  tools/                  # 项目检查、导出和开发期辅助工具
docs/three-kingdoms/
  development-plan.md     # 本路线与验收依据
```

规则与显示分开：UI 不直接扣资源、改伤害或生成角色；它发出命令，规则层校验并更新状态。武将、兵种和城市使用稳定字符串 ID，存档不依赖节点路径。静态定义用 Godot Resource，运行中的生命、士气和归属独立存储，避免修改共享 Resource 导致同类部队一起变化。

测试覆盖真实风险：命令取消、绕障碍失败后的恢复、友军伤害过滤、士气状态切换、招募去重、每日结算只执行一次、战斗回写只执行一次、存档往返一致性。不要为每个纯显示函数编写对应的实现镜像测试。

## 6. 存档、性能与质量门槛

### 存档

只在稳定的战略阶段保存。保存结构包含 `schema_version`、日期、势力、城市、资源、武将实例、军队和事件进度。写入临时文件，校验后替换正式文件并保留上一个有效备份；未知版本或损坏数据给出恢复选择，不能静默清空。局内结算使用唯一战斗标识，避免恢复后重复发奖励。切片发布前完成跨进程保存与读取验证；早期原型数据允许迁移或显式重开，不承诺永远兼容未发布存档。

### 性能

以当前目标 Windows 电脑实测为准，目标是 1280×720、84 个角色与完整战术规则下稳定接近 60 FPS。M0、M2、M5 各记录一次测试机器、单位数、场景和帧时间；M6 连续采样至少 60 秒，关注 95% 帧是否在 20 ms 内以及是否反复出现超过 50 ms 的帧。该目标需测量验证，不能因灰盒流畅就宣称完成。

路径由小队层计算，士兵做有限局部避让，避免每帧给每个士兵全图寻路。AI 感知和目标搜索按固定频率分批执行。先测出热点再优化，不提前构建联网同步或大规模 ECS 框架。

### 每个阶段的完成定义

1. 本阶段验收表能够按操作复现，已知限制写清楚。
2. 工程导入与运行无脚本错误；相关规则测试和基础场景检查通过。
3. 操作或画面变化必须实际渲染并试玩，不能只检查数值与节点属性。
4. 游戏逻辑或资源变更运行仓库 `tools/check.ps1`，并运行新项目自己的相关检查；逐步将新项目检查接入统一入口。
5. 只提交本阶段相关代码、素材、测试与文档，不提交 `.godot/`、临时截图、导出程序和本地存档。
6. 阶段成果正常提交并推送至约定远端；核对分支和远端提交，报告提交编号。检查通过后推送可试玩成果，玩法反馈可在下一个小任务修订。

## 8. 试玩反馈如何进入开发

每次交付用四句话说明：**这次能做什么、怎么启动和操作、哪些内容尚未加入、希望重点体验什么**。用户可在任何阶段提意见，无需等整期完成。

反馈记录到具体行为，例如“右键后队伍在墙角停住”或“敌人被包抄却看不出影响”。先修阻止操作的错误，再调整影响核心体验的设计，最后处理美术和内容扩充。纯偏好变更也保留原话，并更新尚未开始的任务依赖；不默默扩大当前阶段范围。

每阶段结束标记为“实现待试玩 / 根据反馈调整 / 验收通过”，只有已实现的功能写进版本说明。截图是展示证据，实际可玩版本才是验收对象。开发时长在第一轮控制和战斗原型后再估，不给未经验证的上线日期保证。
